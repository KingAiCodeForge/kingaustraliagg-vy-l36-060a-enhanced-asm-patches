**Purpose:** 3-bank split binaries and Capstone M680X disassemblies of the VY V6 ECU ROMs.

> **⚠️ NOTE (Feb 10, 2026 — UPDATED Feb 14):** The Capstone `.asm` files were generated by
> `split_and_disassemble.py` using **Capstone M680X** in recursive descent mode. Despite earlier
> warnings, testing on Feb 14 confirmed that this mode **DOES correctly decode HC11 prebyte

>
> Additionally, GNU m6811-elf (`_gnu.asm`), udis (`_udis.asm`), and the custom Python disassembler
> all produce correct HC11 output. See comparison tables below for quality differences.

## Why 3 Banks?

The 68HC11 has a 16-bit (64KB) address space. The 128KB ROM uses bank switching:

| Bank | File Offset | CPU Address | Size | Contents |
|------|-------------|-------------|------|----------|
| Bank 1 | `$00000-$0FFFF` | `$0000-$FFFF` | 64KB | RAM, I/O, code, calibration, vectors |
| Bank 2 | `$10000-$17FFF` | `$8000-$FFFF` | 32KB | Engine code continuation (dwell calc, TIC3 ISR, dense code) |
| Bank 3 | `$18000-$1FFFF` | `$8000-$FFFF` | 32KB | Transmission/diagnostic overlay |

Banks 2 & 3 overlay into the `$8000-$FFFF` window via hardware bank switching.

> **⚠️ CORRECTION (Feb 12, 2026):** Bank 2 (0x10000-0x17FFF) was previously described as
> "Transmission/diagnostic overlay" and Bank 3 as "Idle/accessory overlay". This was WRONG.
> Per Antus (BANK_SWITCHING_AND_ISR_ANALYSIS.md), Bank 2 contains **engine code continuation**
> (97% dense code including dwell calc and TIC3 ISR), while Bank 3 (0x18000-0x1FFFF) is the
> **transmission processing** overlay. The file header comments in `.asm` files may still show
> the old descriptions.

## GNU m6811-elf Disassemblies (_gnu.asm) — Feb 14, 2026

Generated using the GNU m6811-elf toolchain (`68HC11_Reference/m6811-elf/bin/`):
- **GCC** 3.3.6-m68hc1x-20060122
- **binutils** 2.15 (assembler, linker, objdump, objcopy)
- **GDB** 6.4 (debugger + HC11 simulator)

### Process
```
# 1. Wrap raw .bin as HC11 ELF (set base address)
objcopy -I binary -O elf32-m68hc11 -B m68hc11 --change-section-address .data=0x8000 bank2.bin bank2.elf

# 2. Disassemble with HC11 instruction set
objdump -D -m m68hc11 bank2.elf > bank2_gnu.asm
```

## udis (6811.py) Disassemblies (_udis.asm) — Feb 14, 2026

Generated using `udis.py` from `68HC11_Reference/udis/`:
- Full HC11 instruction set, clean assembler-compatible output
- brset/brclr branch targets: verified correct (bug appears fixed)
- **⚠️ LINEAR-SWEEP MISALIGNMENT WARNING (Feb 14):** udis uses linear sweep and
  loses sync in bank2 around `$81A2` — a 2-byte `LDD $9D` is consumed as part of
  a 3-byte instruction, shifting all subsequent addresses by 2-8 bytes. The critical
  hook point at `$81E1` (`STD $017B`) appears at the wrong address `$81D9` in udis
  output. GNU, Capstone, and custom Python all agree on `$81E1`. This is a fundamental
  limitation of linear-sweep in variable-length HC11 code — **do not trust udis addresses
  for patching without cross-checking against GNU or Capstone.**

#### 4-Way Cross-Check at Hook Point $81E1 (Feb 14, 2026)

Validated `STD $017B` at file offset `0x101E1` (bank2 CPU `$81E1`) — the only
write to dwell intermediate RAM in the entire 128KB binary. This is the hook
point for the spark cut patch.

| Tool | Reported Address | Decode | Result |
|------|-----------------|--------|--------|
| Custom Python | `$81E1` | `FD 01 7B  STD $017B` | ✅ Correct |
| GNU m6811-elf | `$81E1` | `fd 01 7b  std 17b` | ✅ Correct |
| Capstone | `$81E1` | `FD 01 7B  std $017b` | ✅ Correct |
| udis | `$81D9` | `FD 01 7B  std $017B` | ⚠️ Wrong address |
| Raw hex dump | offset `0x01E1` | `FD 01 7B` | ✅ Ground truth |

Hook is identical in all 3 ROM variants (STOCK, v1.0a, v1.1a). See `custom_ose_$060_445_plan.md` §3.1 for full analysis.
